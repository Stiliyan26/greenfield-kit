# Design an interface

Read the product brief, existing code, and `DESIGN.md` if there is one. Preserve an approved design system for ordinary new screens. For a new product or a full replacement, follow [greenfield.md](references/greenfield.md) and use [choose-a-look.md](references/choose-a-look.md) to make intentional visual choices. The client brief wins over either reference.

1. Identify the user's task, device, important information, and the states that could change the layout. Choose one difficult representative task that exposes weak hierarchy (dense data, a warning or conflict, and long real-language content). Ask only about material gaps.
2. For a new visual world or substantial redesign, before drawing research 3–5 relevant production screens for that task. For a small change in an approved system, first use its existing screens and consult external references only for an unsolved pattern. Use Mobbin MCP when available, starting with task-specific searches rather than style words; inspect the actual screen images, not just result titles. Supplement with user references or accessible product examples as needed. For each useful reference, record its link, the specific hierarchy, interaction, or density decision worth learning from, and what not to copy. If reference access fails, say so and use available examples; do not fabricate citations or claim a research pass happened. Component galleries can inform a control, not the whole screen's product structure. Keep this short reference-to-decision record beside the candidate or in the project's design evidence folder.
3. For a new visual world, write a distinct direction contract for each option before coding: a product-specific source idea, a layout sketch, 4–6 named colors, type roles, one recognizable detail, and which reference decisions it adapts. Name the closest generic template each direction risks resembling and the compositional change that avoids it. Use `frontend-design` when available to challenge defaults. Reject directions differentiated only by palette, font, or card styling.
4. Build the difficult representative screen first in two or three distinct, locally inspectable directions using the same realistic data and state. Check its full-size desktop and phone arrangement before expanding each viable direction to the other representative screens in the studio. For a settled visual system, use its existing components and tokens instead of inventing new directions. Include loaded, empty, long-content, loading, save/error, and permission states where they matter; give keyboard focus a visible treatment.
5. Run the [visual quality gate](references/visual-quality.md) on the rendered work at desktop, tablet, and phone widths. Compare full-size captures with the references for the specific qualities noted in step 2, not for a matching brand. Record concrete defects and revise the underlying hierarchy or composition when a candidate is generic; do not polish it with colors and shadows alone. Reopen the captures after revision. Do not present a candidate as finished when it still fails the gate; explain what remains unverified if rendering is unavailable. A passing typecheck does not establish design quality.
6. Let the user choose and refine a named revision. Record its palette, typography, layout, interaction, and state decisions. Build production screens only after the user approves that revision. An earlier approval remains valid for small fixes that preserve the design.
7. List the pieces to reuse, the data each screen needs, and any remaining questions for `plan-feature` and `deliver-feature`.

In a greenfield project, use its local studio and saved selection as the choice record. If none exists, use `greenfield-mode` to initialize and populate one. Follow the commands and paths documented by that project; do not assume a framework, stylesheet path, or design-review script exists.
